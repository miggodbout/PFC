### Rebuilding the chip history on a new phone

`15-suggestion-list` deleted the seed list and made the needed-line chips grow
from records instead. The history index that keeps them alive past the end of a
job lives in `localStorage`, so **a new phone, or a reinstall, starts with none.**

Miguel spotted the gap himself: the common sizes are sitting in the project
Sheets, so why can a new phone not go and get them?

- **It can, and discovery is already free.** `handleListProjects` at
  `Code.js:182` walks every Sheet in the Projects folder, and `14` put the
  finished-building test in the **phone**, not the server. So a new phone already
  receives the id of every job ever run. A `rebuild-suggestions` action reading
  one tab per Sheet is a small piece of work.
- **Why it waits:** the closed-jobs rule above. Also, a new phone recovers nearly
  everything without it, because `15` made `get-project` return every record state
  — open the two live buildings and their whole history arrives. What is missing
  is wording unique to a **finished** job, and a door size is the least
  job-unique thing there is.
- **The risk if it is built as a one-shot call:** up to ~50 Sheet opens against
  the 6 minute Apps Script execution limit. Read only the Deficiencies tab, four
  columns, not the whole Sheet.
- **It repairs more than a new phone.** The same action fixes a corrupted or
  hand-cleared index.
- **The seams 0.2 must leave, listed in full at the end of `15`:**
  `list-projects` keeps returning finished buildings, `get-project` keeps
  returning every record state, the index row shape stays re-feedable, and the
  index stays its own store.
- **Source:** Miguel, 2026-08-08, during `15-suggestion-list`.

### An abandoned job never leaves the Tracking list

A building leaves Tracking in 0.2 only when it reads Complete. Nothing else moves
it. So a job cancelled part way through — say at 60% — never reads Complete and
its row sits in the Tracking list forever.

- **Why it waits:** Miguel was offered a two-way `Closed` checkbox in Admin on
  2026-08-08 and turned it down. `13-admin-changes` already raises `_Config` to
  version 2, so the flag itself was nearly free. He chose against it for two
  reasons: a stored flag can disagree with the computed numbers, and 0.2 has no
  Archive door, so a mis-tapped flag would hide a live job with no way back inside
  the app.
- **Why a one-way switch was never offered:** without an Archive door, closing a
  building you did not mean to close would be permanent in the app. If the switch
  is ever built, it must close **and** reopen.
- **What it costs today:** one dead row per abandoned job. One or two buildings are
  live at a time, and about 50 are expected over the life of the tool, so this
  grows slowly.
- **What forces it:** the first job that actually gets cancelled, or the Tracking
  list carrying more dead rows than live ones.
- **It arrives with the Archive window, above.** Once a closed building has a door
  to sit behind, the switch has somewhere to send one and a way to get it back.
- **Source:** `.scratch/pfc-control-0.2/issues/14-building-archive.md`, answer 3,
  resolved 2026-08-08.

### The GC punch list — deficiencies found months after a building is finished

A building is complete. The GC does a final walk and finds a list of problems.
Miguel, 2026-08-07: "deficiencies often show up months after a building is
complete. GCs come and do a final check and find issues."

- **Why it waits:** Miguel ruled it out of 0.2 on 2026-08-07. It is a workflow,
  not a rule. It needs an archived building to reopen and a deleted local copy to
  come back, and neither of those exists yet.
- **What forces it:** the first GC walk on a building tracked in this app. That
  is a date, not a maybe.
- **What it runs against, all already decided:**
  - `03-local-copy-rules` deletes archived buildings from the phone. The GC is
    standing in an empty building with no signal and no copy.
  - `14-building-archive` makes Archive computed, so a new record un-archives a
    building by itself. Nobody decided whether that is right.
  - `01-deficiency-record-fields` ruled out author and promised date. A GC item
    may need both, and adding them changes the Deficiencies tab columns fixed in
    `02`.
- **The seam that keeps it possible:** records are never deleted and never moved,
  and every record carries an id made on the phone. A punch list is more records
  on the same tab. Nothing in 0.2 closes the door.
- **What was carved out and built in 0.2 anyway:** an item that already reads
  Complete when a flag lands. It fires in a live building with no archive
  involved, so it could not wait. Answered in `11-rollup-rules`.
- **Source:** `.scratch/pfc-control-0.2/issues/16-post-completion-deficiencies.md`,
  which holds the full write-up.

### The script lock blocks every project at once

> **DISPLACED from 0.3 on 2026-08-09.** 0.3 is the Archive release. This is one of
> the three crew-access items, and it has no version yet. See the top of this file.

The backend takes one lock for the whole script. A write to Building A blocks a
write to Building B, even though the two Sheets have nothing to do with each
other.

- **Why it waits:** Miguel is the only editor in 0.2. One person cannot collide
  with themself, so the cost is nothing today.
- **What forces it:** the crew getting edit access. Several people on several
  units at once will queue behind each other for no reason.
- **The likely fix:** a lock per project instead of one lock for the script.
  `LockService.getDocumentLock()` exists for this, or a key built from the
  project id.
- **Source:** `.scratch/pfc-control-0.2/issues/07-apps-script-write-limits.md`.

### Private repo and a move to Cloudflare Pages

The repo is public, because free GitHub Pages requires it. That publishes the
source, CLAUDE.md, the commit history, and every planning note in `.scratch/`.

- **Why it waits:** it is not security, and treating it as security is the
  danger. The backend address sits in `control/shared/common.js` and must ship
  to every phone that runs the app, so any reader of the live site has it. A
  private repo hides the notes, not the data.
- **What forces it:** nothing external. It is Miguel's call on whether his
  planning stays public.
- **The likely fix:** make the GitHub repo private, then serve the app from
  Cloudflare Pages. The free tier builds from a private repo, which GitHub Pages
  will not do. No cost.
- **The cost:** the app URL changes. Printed QR codes point at the camera app and
  are safe, but saved shortcuts on crew phones need updating.
- **Do not confuse it with this list's real fix:** the Apps Script deployment is
  set to Anyone. Google login in 0.3 is what closes that, and it closes it at
  the backend, where code cannot be read. Decide the hosting question separately.
- **Rejected already:** putting a login gate in front of the whole site. It
  fights the Service Worker's offline cache, and a worker in gloves scanning a QR
  code should not meet an email prompt.
- **Source:** raised by Miguel 2026-08-06, reviewing public repo exposure.

## Decide when 0.3 is charted

### How 0.3 gets a stopping rule

Miguel named his own failure mode on 2026-08-08: "scope creep / analysis
paralysis is a real issue for me, I'll keep planning and perfecting for days /
weeks without writing any code." He asked for techniques against it, aimed at
0.3, since 0.2 is already well planned.

**The diagnosis, and it is not that he planned too much.** The 0.2 planning paid
for itself — the id-made-on-the-phone rule and the keyed outbox would have cost
days to find in code and a lost save on site to find in the field. The problem is
that the map's destination is "every decision settled", which is a completeness
test, and completeness has no edge.

Four techniques were proposed. **Nothing is adopted yet.** Decide when 0.3 charts.

1. **Build the spine before deciding the details.** The biggest lever. A question
   costs an hour against a sketch and five minutes against a running screen.
   Ticket 06 is the evidence: eight decisions in one sitting, because there was a
   prototype to react to. Chart only the decisions that are expensive to reverse,
   build, then let the working app raise the rest.
2. **Every ticket carries a default answer** when it is created: "if nobody
   decides, this is what gets built." An unanswered ticket then ships its default
   instead of blocking. Paralysis needs a blocked state to live in.
3. **A "decide it while building" bucket.** Wording, spacing, the order of two
   fields — reversible in a minute, so the build session picks and changes it
   later if wrong. Today a 200ms header flash and the whole offline queue go
   through the same machinery.
4. **Budget the version, do not scope it.** Fix 0.3's size up front — one window,
   six tickets, one weekend — and make features compete for it. Miguel invented
   half of this himself with the one-window guideline in `CLAUDE.md`.

Recommended: 1, 2 and 3 together. They cost nothing to adopt and they attack the
mechanism rather than the symptom. A time box on charting was considered and held
in reserve, because it treats the symptom.

- **Source:** Miguel, 2026-08-08, at the end of `06-deficiency-entry-screen`.

## Review later, not tied to one version

### The 0.5 materials export needs a cleanup step, and 0.5 must not forget it

`12-logger-door` rejected structured dropdowns for the needed line. Free text
won on speed. Part of what paid for that choice was Miguel's own answer: bad
data gets "a look over at export".

**That look-over is now a promise, and no ticket owns it.** 0.5 builds the
material order summary. If it prints a raw count of free-text lines, then
`32" 6" RH` and `32" 6 RH` are two different doors on the order, and the trade
made in `12` fails quietly at the worst moment.

- **What 0.5 owes:** a review screen before the order prints. It groups the
  needed lines, shows near-matches side by side, and lets Miguel merge two
  spellings into one.
- **What reduces the size of that job:** `15-suggestion-list`. Good suggestions
  mean fewer spellings reach the export. Weak suggestions mean the export screen
  carries the whole load.
- **`15` closed 2026-08-08 and shrank this job a lot.** Three of its rules attack
  the same problem before export: chips are sourced across every building and
  survive a job ending, so the vocabulary keeps growing; a **near-match prompt on
  Save** offers the stored spelling before a near-duplicate can be written; and
  `17`'s subtype dropdown already took the closed-set words out of the text. The
  example in the paragraph above no longer happens — `32 6 RH` and `32" 6 RH`
  normalise to the same string, so the prompt catches it at entry. **The export
  review screen is still owed**, because nothing catches a size typed loose the
  very first time it is ever used.
- **Source:** Miguel, 2026-08-07, during `12-logger-door`.

### A parser that reads a loose needed line and prints the standard form

Miguel raised it on 2026-08-08 while resolving `15-suggestion-list`, and ruled it
out of 0.2 himself in the same conversation. His words: "maybe we should have
designed a system that deciphers different nomenclatures and cleans them up in
the backend... this is quite a complicated add though."

- **What 0.2 already does instead.** Tap a chip and the stored text is saved, not
  what you typed. Type loose and the Save prompt offers the stored text. So every
  line that has been typed before is already cleaned. **Only a size logged for the
  very first time goes in raw** — a handful per job, and fewer every job as the
  history index grows.
- **Why it is not cheap.** A parser must guess. `5 1/4 MDF` on a baseboard and
  `32 6 RH` on a door are both numbers, and telling them apart needs a grammar per
  item, a screen to edit that grammar, and a way to correct it when it reads
  wrong. That is the four-field structured form `17-reason-list-scope` turned
  down, wearing a coat.
- **A middle option, if this is ever picked up:** a tidy rule that only runs on
  items told it may. It was sketched and set aside because the per-item setting is
  another Admin list, which is `13-admin-changes` again.
- **Source:** Miguel, 2026-08-08, during `15-suggestion-list`.

### An optional per-subtype hint on the needed box

`15-suggestion-list` gave each item a `hint` — the grey placeholder naming what
each part of the needed line means, such as `Size   Jamb   Swing`. It is **one
hint per item**, and it does not change with the subtype.

Miguel took that reluctantly: "I don't like this but adding 8 different hints is
egregious." He is right on the count — per-subtype hints go from fourteen strings
to about thirty, and every subtype added in Admin then needs one more.

- **What is wrong with it today.** A bypass door has no swing, so its placeholder
  names a term it does not use.
- **Why it is safe to wait.** The hint is a reminder, not a rule, and the Subtype
  dropdown sits directly above the box, so you can see which kind of door you
  picked.
- **The seam is already there.** `hint` is a per-item key in `_Config`. An
  optional per-subtype override needs no reshaping, only a place to hold it and a
  fallback to the item's hint when it is blank.
- **Source:** Miguel, 2026-08-08, during `15-suggestion-list`.

## Known and accepted, no action planned

### The CORS technique carries no promise from Google

The app avoids a browser check by labelling its data as plain text. This follows
the web standard and works today. Google has never documented how Apps Script
handles this, so Google could change it without a release note.

- **Why nothing is done:** the app already has a second path (JSONP) that works
  when the first one fails. The insurance is in place.
- **What forces it:** saving starts failing for everybody at once, with no change
  on our side. Check this first if that ever happens.
- **Source:** `.scratch/pfc-control-0.2/issues/07-apps-script-write-limits.md`,
  section 6.
