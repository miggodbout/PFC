# PFC Control 0.2.1 — the build list

Settled 2026-08-15 with Miguel, from the 0.2 test week. **This is the whole
release. Nothing else goes in it.** Anything touching record types, reason lists,
the History tab or bulk belongs to 0.3.

Sorting and reasoning: `.scratch/test-week-triage.md`.

**Fourteen items.** Three of them turned out to share one root cause, and two
reported bugs turned out not to be bugs at all.

---

## The one root cause behind three items

`classifyCallFailure` (`common.js:1668`) sorts a failed call into two buckets:
the phone never reached the server, or it reached it and the write was refused.
`offline` and `timeout` go in the first bucket and cost nothing. **Everything
else, including `blocked`, goes in the second.**

But `blocked` — "the browser could not read the reply" — is what a **weak signal
produces**. So a bad hallway is being read as a broken deployment. Three
complaints come out of that one misreading:

- The E2 message tells Miguel to tell the Admin when the signal is just bad.
- Each weak-signal attempt burns a try, so ten of them hold the edit and force a
  manual re-queue.
- The technical log fills with E2 entries that mean nothing.

**The fix is one idea: has this phone ever reached the server?** A call that
succeeds sets a flag. After that, a `blocked` failure is treated as a connection
problem — no code, no admin message, no burned try. Before that, it keeps the
code, because then it really is broken.

## The list

### 1. Install sheet — rebuild it

**A bottom sheet**, rising from the bottom edge, page dimmed above. Near the
thumb, which is where the phone is held one-handed.

**It never shows when the app is already installed.** Check
`matchMedia('(display-mode: standalone)').matches || navigator.standalone`.
**Never on first paint** — wait until the Hub has drawn and its data has loaded.

**Android.** Capture `beforeinstallprompt`, call `preventDefault()`, keep the
event, and show the sheet only once it has fired. The Install button calls
`prompt()` **inside the tap handler** — it will not work outside a user gesture,
and it can only be used once per fired event.

```
Add to Home Screen

This site works like an app. Install it to keep your saved work.

[ Install ]   [ Later ]
```

**iOS.** No install API exists on any iOS browser, so instructions are the only
option. Step 1 names both buttons, because iOS 26's default Safari layout hides
Share behind `•••` while older layouts and older phones show it directly. The
page cannot read which layout is set, so it must not guess.

```
Add to Home Screen

1  Tap Share, or tap ••• in the browser bar.
2  Scroll down.
3  Tap Add to Home Screen.
4  Tap Add.

A browser tab can delete your saved work after 7 days.
The Home Screen app keeps it.

[ Later ]
```

**The 7-day line is iOS only.** It is a WebKit rule and it is not true on
Android. Confirmed at the primary source — WebKit, *Full Third-Party Cookie
Blocking and More*: script-writable storage is deleted "after seven days of
Safari use without user interaction on the site", and "web applications added to
the home screen are not part of Safari and thus have their own counter."

**`Later` stores a date and the sheet stays away for 14 days.** A permanent
**Add to phone** row on the Hub opens the same sheet at any time, so it is never
lost.

**Where the wording comes from.** `Add to Home Screen` is Apple's own Share-sheet
row, capitalised as Apple capitalises it. `Install` is Chrome's own dialog
button. `Later` is the dismiss label a shipping library uses. The one sentence
that is ours is the body line: the standard `This site has app functionality.`
fails `docs/crew-words.md`, because "functionality" is not a word the crew uses.

**Every string goes through `docs/crew-words.md` before it ships.** New words to
check: Install, Share, Home Screen, Tap, Later, browser, tab.

### 2. `manifest.json` — add a 192×192 icon

Only 512×512 is declared. Chrome's install criteria ask for both. Without it,
`beforeinstallprompt` may never fire, so item 1 cannot work on Android.

### 3. Hub — cards and wording

- **Remove `Deficiencies`.** Logging already does this, and two cards for one job
  is how a person taps the wrong one.
- **Remove `Materials`.** It is really the 0.5 export. A card reading "Coming
  soon" for six months stops meaning anything.
- **Keep `Reports` and `Archive` greyed.** Archive is a deliberate seam — see the
  comment at `control/index.html:93`. Do not remove it to tidy the grid.
- **Rename `Logging` to `Log`.** An instruction, not a category. Touches the Hub
  card, the tab title and the screen header.
- **Subtitles lead with the verb**, so a card says what you do:
  `Tracking → See what is done`, `Log → Log an issue`,
  `Set Up Building → Create or change a building`.

### 4. Centre the Logging flag glyph on the Hub

`theme.css`. It sits off-centre in its card.

### 5. Centre the refresh ring on the header text

`common.js`, the `.ptr` element. It used to sit too low, now not low enough, and
on **Set up building** it overlaps the header outright.

### 6. Queue screen — a word per row

The outbox sends **one edit at a time**, so a spinner on every row says all of
them are working when only one is.

- The connection is stated **once**, at the top: `▨ Offline · 3 edits waiting`.
- Each row says its own state in words: `Waiting`, `Sending`, `Did not save`.
- Only the row actually being sent gets anything that moves.

### 7. Sync bar — no age under the red bar

`syncBarHtml` (`common.js:2818`) still draws the `updated 1:22 AM` sub-row while
a save is in the air. **Suppress the stale sub-row whenever `Queue.sending()` is
true.**

### 8. Refetch when the app comes back — and it fixes the "Last updated" bug

**These are one item.** `markFresh()` clears the age line, and it only runs when
a fetch **succeeds**. A fetch only happens on screen load or pull-down. So after
the phone reconnects, nothing fetches, so the line never clears.

There is no timer anywhere in this app, by design (`common.js:2586`), and that
does not change. What changes: **when the app comes back to the front, refetch
the open screen if its copy is more than 2 minutes old.** Glancing at the app in
a hallway stays free. Walking to the next unit gets fresh data — and clears the
line by itself.

### 9. E2 — stop blaming the admin for a bad hallway

Per the root cause above. Once the app has reached the server on this phone:

```
The app could not reach the server. The signal here may be weak. Try again.
```

Before it ever has, the message and the code stay exactly as they are. **The code
is still written to the technical log in both cases** — nothing is lost for
debugging.

### 10. The outbox keeps trying

A connection-style failure **never burns a try**, exactly as `offline` and
`timeout` already do not. It retries on the existing 5-minute beat for as long as
the app is open, and wakes on reconnect and on returning to the app.

Only a **real refusal from the server** counts toward `QUEUE_MAX_TRIES`. Ten of
those still hold the edit and show it in the Queue window for a person to decide
about. **No job is ever deleted by the app**, and that rule does not move.

### 11. Logger — Reason above Needed

Order today: Type → Item → Subtype → **Needed** → Count → **Reason**.
New order: Type → Item → Subtype → **Reason** → Count → **Needed**.

### 12. Logger — Needed becomes optional

`logging/index.html:846` requires it on every Deficiency. Waiting is already
exempt.

**Why.** Of 27 live records, `needed` holds `Adjust`, `Install`, `Flip Privacy`,
`Adjust slabs`, `Screws broken in jamb`. Those are not materials — they are
actions invented to get past a required field. The column that feeds the 0.5
material order filled with to-do notes in one week.

No prompt when it is left blank. A confirm would fire on most records, which is
a tap on the common case to catch the rare one.

### 13. Progress bar — weight it

**The bug in one ratio: hardware is 54% of every count in the app and 6% of the
work.** Each unit holds 13 items — 4 doors, 2 baseboard, 7 hardware — so a ball
catch counts the same as a unit door.

Miguel's own rates, 2026-08-15:

| Phase | Rate | Days per unit | Weight |
|---|---|---|---|
| Phase 1 | 2 people, 1.25 units/day | 1.60 | **68%** |
| Phase 2 | 1 person, 1.75 units/day | 0.57 | **24%** |
| Phase 3 | 1 person, ~6 units/day | 0.17 | **7%** |

Elsliger 36-B reads **36%** today. Weighted it reads **58%**, which is what
standing in the building feels like.

**One bar, one fill, one colour** — the weighted number. The three phase runs
`phaseRunsHtml` draws today are replaced: they were each measured against the
whole building, so a phase 76% finished drew a short run and the three still
totalled 36%.

Under it, one line of text, naming each phase as that building names them:

```
Elsliger 36-B
[###############...........]  58%
Phase 1 76% · Phase 2 21% · Phase 3 18%
30 of 36 units started · 0 done
```

**Started units need no backend change.** `list-projects` already sends
`unitsDone` and `unitsNotStarted`; started is the leftover.

**Where the weights live.** In `common.js` for now, read from the building's own
config when it has one:

```js
var PHASE_WEIGHT = { phase1: 1.60, phase2: 0.57, phase3: 0.17 };
weight = phase.weight || PHASE_WEIGHT[phase.key] || 1;
```

0.3 adds the field to the building settings tab and the fallback quietly stops
being used. No Sheet is touched in 0.2.1.

**Phase names stay `Phase 1` / `Phase 2` / `Phase 3`.** That is what
`DEFAULT_PHASES` ships (`common.js:252`) and what the crew says out loud, and the
numbers carry the order of the work in a way names do not.

### 14. Window names and subtitles

Covered by item 3. Names stay as they are otherwise — `Tracking` the section and
`Buildings` the header was decided deliberately, and is not to be tidied.

## Two reports that were not bugs

**"After fixing a flag the item is marked Complete automatically."** Nothing is
written automatically. The item was set Complete **before** the deficiency
landed; the app displayed In Progress while the flag was open and stopped masking
it when the record was marked Fixed. An item that was In Progress does get asked,
by the green card at `unit.html:393`. Miguel confirmed no change is needed.

**"Need item-specific reasons."** They exist, but an item can only ever **hide** a
reason, never add one. That is the real limit, and 0.3 fixes it.
